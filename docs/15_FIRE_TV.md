# 15 — Lumina TV: the Fire TV / Android TV app

**Status:** built and run on an Android TV emulator, **not yet run on a real Fire TV Stick**. Everything below is
labelled with how it is known, because this project has repeatedly built on claims nobody checked:

* **[verified]** — run in this work, with the result observed (screenshot, log line, tool output).
* **[docs]** — taken from the vendor's own documentation, not run.
* **[not proven]** — believed, untested; needs the real device.

The code is in `tv/` (its own Gradle project). The PC app is untouched by it apart from two pieces of shared contract
(§4). Read `AGENTS.md` first: the hard rules apply here too (no evasion of human checks, no infringing fixtures, never
a store).

---

## 1. Why a separate app, and what is deliberately left out

The PC app is an Electron program that bundles Windows `aria2c`, `yt-dlp`, `ffmpeg` and 7-Zip, runs a download
scheduler, an IDE, a terminal, an MCP client, an in-app browser with a shield, a DLNA server, USB export and sync.
None of that belongs on a TV stick with **8 GB of storage and 2 GB of RAM** [docs: Amazon device specs], and none of
the Windows binaries run on Android at all.

So the TV app is a **new native Android program** that does the one job the TV is for — find a song or video, play it
now or keep it — and nothing else. Left out on purpose (still in the PC app, unchanged): torrents and aria2, the IDE
and terminal, MCP, the in-app browser and shield, DLNA sharing, USB export UI, Lumina Sync, the Lengine framework.

## 2. The device [docs unless stated]

Amazon's device page lists the Fire TV Stick 4K Plus as: MediaTek MT8696D, 4x Cortex-A55 at 1.7 GHz, **32-bit ABI**,
2 GB RAM, 8 GB storage, **Fire OS 8 = Android 11 (API 30)**, H.264/H.265/VP9/AV1 hardware decode up to 4K60, Opus and AAC
audio. (One review site says Android 7.1; Amazon's own table says API 30 and was used.) **Not verified:** the free
storage actually left for apps, and the ABI list the OS reports (`adb shell getprop ro.product.cpu.abilist`).

## 3. Decisions

| Question | Decision | Why |
|---|---|---|
| Native, WebView, or React Native? | **Native Kotlin + Jetpack Compose** | D-pad focus, the launcher banner and background audio are first-class in the platform. React Native would still need native modules for extraction and playback, so it adds a JS engine on a 2 GB device for the sake of reusing a small amount of logic. |
| How to get streams without Python? | **NewPipeExtractor v0.26.5**, in-process | yt-dlp needs a Python runtime; on 32-bit ARM with 2 GB that is heavy and fragile. The extractor is pure Java, a few MB, actively maintained (last push seen 2026-10-21). **Cost: it is GPL-3.0, so `tv/` is GPL-3.0** (the PC app stays MIT; they are separate programs). |
| Toolchain | Gradle 8.14.6, AGP 8.13.2, Kotlin 2.2.21, compileSdk 36, **targetSdk 30**, minSdk 25 | The newest AndroidX (mid-2026) needs AGP 9.1+ / compileSdk 37; AndroidX is pinned to the last releases for compileSdk 36. targetSdk 30 equals Fire OS 8, so what was tested is what the stick does. |
| Where do files go? | App folder on the chosen volume, **PC app's USB layout and names** | See §4. A USB stick in the Fire TV is the realistic home for a library. |
| Quality | Original audio, untouched (Opus/AAC, no transcoding); streaming default 1080p, saved video default 720p | Same rule as the PC app's default preset ("Original audio"). |

## 4. The contract with the PC app (so the two never drift)

* **File names and folders.** `src/core/portable.ts` (PC) and `tv/.../core/FileNames.kt` (TV) must name files
  identically: `LuminaMedia/Music/Artist - Title.ext`, `LuminaMedia/Videos/Title.ext`, FAT-safe segments.
  `shared/contract/portable-names.json` was **generated by running the PC functions**; both test suites read it
  (`tests/portableContract.test.ts`, 30 tests; `FileNamesTest`). Change a rule on one side and the other side's tests
  fail. **[verified]** both pass.
* A drive or folder therefore moves between the apps with no renaming. **[not proven]** end to end with a real stick;
  proven only as "the TV app writes exactly the names the PC app would".
* Not yet shared: Lumina Sync (device chain). The crypto core is already portable TypeScript; the TV side is not written.

### 5d. Memory for 1 GB sticks (2026-10-24)

Method: an emulator limited to 1 GB (`-memory 1024`, MemTotal 997 MB, 192 MB app heap), the same page tour each time (Home,
Videos, Music, Settings, Home, Videos, Music, Playlists, Home, 12 s apart), then `dumpsys meminfo`. Total PSS:
debug build before changes 170 MB; debug build after 171 MB (no real change: the tour never fills the picture cache);
**release build 110 MB** (code 26 MB against 84 MB in the unminified debug build). So the largest saving is running the
release build, not a code change. The stick's own debug build idles at about 120 MB with the app in the background.

Changes, all decided by `core/MemoryPlan` from RAM size (tests: 160 pass): one shared picture loader (the colour finder used to
create a new loader, with its own cache, per cover), its memory cache capped at 8% of the app heap on a small device (15%
otherwise) and trimmed when the system asks, a 96 MB disk cache, the player reads at most 20 MB / 45 s ahead on a small device
(48 MB / 90 s otherwise), and the page backdrop is painted at two thirds size there and stretched. Covers, video and audio are
decoded at the same size and quality as before.

Also (2026-10-24): `app/src/main/baseline-prof.txt` (wildcard rules for Lumina's own code, Compose, TV Material, Media3, Coil)
so the system compiles the hot paths at install time; on the stick `dumpsys package` reports `status=speed-profile` after
`cmd package compile -m speed-profile -f com.lumina.tv`. The release build (4.4 MB) was signed with the **debug key** for a
local test and installed on the stick beside the debug build (`com.lumina.tv` and `com.lumina.tv.debug`); a build signed with
the real key will need this one uninstalled first. Smoothness on the stick was **not measured**: its display was asleep.

Not proven: any effect on a real 1 GB stick (the emulator is x86 and has no such stick's Fire OS overhead); video playback
memory (not measured); the caps only matter when the cache would otherwise fill, which a longer session does. A release
build needs the real signing key (section 7); one signed with the debug key was used here only for the measurement and
cannot be updated by a real-key build.

### 5f. Search: no surprise keyboard, no surprise sidebar (2026-10-24)

Reported on the real stick: opening Search jumped straight to the keyboard, and closing it dropped the remote on the sidebar, which sat
open over the recent searches (and every time the remote entered the box the keyboard came back, so Down to the recents was
unreachable). Cause: the page asked for focus on the text input itself (which opens the TV keyboard), and that request raced the
shell's own focus hand-off while the old screen was still fading out.

Now (`SearchField`, used by Search, the profile name box and the playlist-link box): the box is a focus target of its own. Landing on
it (the page opens on it, after the 320 ms transition) only lights it. Select starts typing and opens the keyboard. Closing the
keyboard leaves the remote on the box (not the sidebar); Back while typing only stops typing; Down reaches the recent searches; Left
reaches the sidebar. Separately, Back from any screen to Home now lets Home take the remote on its mosaic (`backToHome` in
`AppShell`, cleared by the next key press) instead of leaving the sidebar open holding it.

Seen on the emulator (its keyboard is not the Fire TV one): Search opens on the box, sidebar shut, recents visible, no keyboard;
Select opens the IME, Back closes it with the remote still on the box; Down moves to the first recent search; Back from Search lands on
Home's first tile with the sidebar shut; the name dialog opens lit with no keyboard and Select opens it. **Not seen:** the Fire TV
keyboard itself (it is a separate Amazon window and may behave differently when it closes: the "take focus back" path in
`SearchField.onFocusChanged` is there for that and is unproven), the playlist-link dialog. 168 unit tests pass. The release with this
fix is built but was **not installed**: the stick went offline during the install.

## 7. Building and installing

See `tv/README.md`. In short: `tv/gradlew :app:assembleDebug`, then `adb connect <stick-ip>:5555` and `adb install`.
Fire OS 8 requires an APK signature v2; the build produces one **[verified]**.

### Signing a release

The signing key is the app's identity. Android installs an update only if it is signed with the same key as the app
already on the stick, and the in-app updater relies on that rule. Lose the key and every stick needs a reinstall; leak it
and anyone can ship an "update". So it lives **outside the repository**, and the build never falls back to a throwaway key.

1. **Make the key, once.** Keep two copies somewhere safe and offline, and remember the password:

   ```bash
   keytool -genkeypair -v -keystore lumina-tv.jks -alias lumina -keyalg RSA -keysize 4096 -validity 10000
   ```

2. **Point the build at it.** Create `tv/keystore.properties` (git-ignored, with `*.jks` and `dist/`):

   ```
   storeFile=../../keys/lumina-tv.jks
   storePassword=<the password>
   keyAlias=lumina
   keyPassword=<the password>
   ```

   `storeFile` is relative to `tv/`. Without this file `assembleRelease` produces an **unsigned** APK that cannot be installed.

3. **Build.** `bash tv/tools/release.sh` (needs `JAVA_HOME`, `gradle` and `ANDROID_HOME`). It refuses to run without the
   key, runs the unit tests, builds the minified release, verifies the signature with `apksigner`, and writes
   `tv/dist/lumina-tv-<version>.apk` (the name the updater looks for) with a `.sha256` beside it.
4. **Install.** `adb install -r tv/dist/lumina-tv-<version>.apk`. The release is package `com.lumina.tv`, the debug build
   is `com.lumina.tv.debug`, so both can sit on the stick.
5. **Publish an update.** Raise `versionCode` (it must increase) and `versionName` in `tv/app/build.gradle.kts`, run the
   script, and attach the APK to a GitHub release of `nikhlgoel/lumina`.

A build signed with the debug key (used only to test a release locally) cannot be updated by, or update, one signed with
the real key: uninstall it first.
